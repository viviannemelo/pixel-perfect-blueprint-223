Pre-release Smoketest

A QA skill that tests everything going to production before the deploy and says whether the release can proceed. Running on staging, it has already found 7 bugs that were blocking the deploy.

Uma skill de QA que testa tudo o que vai para produção antes do deploy e diz se o release pode seguir. Rodando em staging, ela já encontrou 7 bugs que estavam bloqueando o deploy.

The problem

Every week, many changes ship to production together, and testing everything by hand on the eve of the release doesn't fit the team's schedule.

Without a fixed process, the outcome depends on who is testing: which changes make the list, how much is tested around each one, and how the go / no-go decision is made. It's in those gaps that a side effect on a neighboring screen slips into production.

The skill replaces that with a single, repeatable gate before every deploy, with the same steps on every release.

How it works

On the eve of the release, someone from QA runs one command, and the skill follows five steps:

  1. Scope: pulls from Jira every change marked as ready for the release. The list comes from the tool, not from a hand-built spreadsheet.
  2. Understand: reads each ticket (description, acceptance criteria and comments) and identifies the affected product area.
  3. Coverage: creates two kinds of tests for each change. Direct tests confirm what was built. Adjacent tests check what's around it, on the same screen or the same data, where side effects usually appear.
  4. Execution: runs everything in the browser. First a fixed set of essential product scenarios, then each change's tests, from most to least critical. Every failure is recorded with reproduction steps, expected and actual results.
  5. Verdict: says whether the release is ready, ready with minor risks or blocked, always explaining why. When it finds bugs, it generates a report for engineering.

The skill is read-only: it doesn't deploy, doesn't change data and doesn't open tickets on its own. Login and two-factor authentication are always done by a person.

Results so far

  • 7 deploy-blocking bugs found on staging, all caught before reaching production — when fixing is still cheaper and no user was affected.
  • The biggest gain comes from the adjacent tests: they look at what's around each change, exactly the kind of failure a ticket-focused test would miss.

O problema

Toda semana, muitas mudanças vão juntas para produção, e testar tudo à mão na véspera não cabe no tempo do time.

Sem um processo fixo, o resultado depende de quem está testando: quais mudanças entram na conta, quanto se testa em volta de cada uma e como se decide se o deploy pode seguir. É nessas lacunas que um efeito colateral em uma tela vizinha escapa para produção.

A skill troca isso por um portão único e repetível antes de cada deploy, com o mesmo passo a passo em todo release.

Como funciona

Na véspera do release, alguém do QA roda um comando, e a skill segue cinco passos:

  1. Escopo: busca no Jira todas as mudanças marcadas como prontas para o release. A lista vem da ferramenta, e não de uma planilha montada à mão.
  2. Entender: lê cada ticket (descrição, critérios de aceite e comentários) e identifica a área do produto afetada.
  3. Cobertura: cria dois tipos de teste para cada mudança. Os diretos confirmam o que foi feito. Os adjacentes verificam o que está em volta, na mesma tela ou nos mesmos dados, onde efeitos colaterais costumam aparecer.
  4. Execução: roda tudo no navegador. Primeiro vem um conjunto fixo de cenários essenciais do produto, depois os testes de cada mudança, do mais crítico ao menos crítico. Cada falha fica registrada com os passos para reproduzir, o resultado esperado e o obtido.
  5. Veredito: diz se o release está pronto, pronto com riscos menores ou bloqueado, sempre explicando o motivo. Quando encontra bugs, gera um relatório para a engenharia.

A skill só lê: não faz deploy, não altera dados e não abre tickets sozinha. O login e a autenticação em dois fatores são sempre feitos por uma pessoa.

O resultado até agora

  • 7 bugs que bloqueavam o deploy encontrados em staging, todos pegos antes de a versão chegar à produção — quando corrigir ainda é mais barato e nenhum usuário foi afetado.
  • O ganho vem principalmente dos testes adjacentes: eles olham para o que está em volta de cada mudança, que é justamente o tipo de falha que um teste focado só no ticket deixaria passar.
