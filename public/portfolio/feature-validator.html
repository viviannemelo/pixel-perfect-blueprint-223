Feature Validator

You type /feature-validator ENG-1234 and get back a published QA report with evidence. In between, the AI reads the code, the merge request, the Figma file and the Jira task, writes the requirements, builds the test plan and runs the cases on staging with Playwright.

Você digita /feature-validator ENG-1234 e recebe de volta um relatório de QA publicado, com evidências. No meio do caminho, a IA lê o código, o merge request, o Figma e a task do Jira, escreve os requisitos, monta o plano de testes e executa os casos no staging com Playwright.

The problem

Good QA is traceable. Every test case should point to a requirement, every requirement to a source (an acceptance criterion, a Figma frame, an MR comment, a piece of code), and every bug to its evidence. Doing that by hand for every feature is slow, so most of the traceability gets lost along the way.

The idea behind this skill: one reference is enough. You give it a Jira task or a git branch — nobody pastes code or requirements — and it discovers the rest of the context on its own.

The solution

The skill runs in four phases, and each one delivers an artifact that feeds the next:

  1. Investigation: reads the diff, the merge request discussions and the Figma file, and maps what doesn't happen on click — crons, queues, emails, reminders, expirations.
  2. Requirements: builds a matrix where every requirement carries its source and its state variables (status, role, feature flag, timezone, empty or filled, first time or recurring).
  3. Test plan: a table where every requirement gets at least one case, plus control cases, end-state checks, post-transition consistency and pairwise state combinations.
  4. Execution (optional): runs the cases by priority with Playwright, marked PASSED, FAILED or NOT TESTED, and publishes a bug-focused report with traces.

Rules that came from real executions: visual assertions compare screenshots against Figma, money or clinical data is read back from the database, and evidence is never forged — if a path is unreachable through the product, the report says so.

O problema

QA bem feito é rastreável. Cada caso de teste deveria apontar para um requisito, cada requisito para uma fonte (um critério de aceite, um frame do Figma, um comentário do MR, um trecho de código) e cada bug para a sua evidência. Fazer isso à mão para cada feature é lento, então a maior parte dessa rastreabilidade se perde no caminho.

A ideia central da skill: uma referência basta. Você passa uma task do Jira ou uma branch do git — ninguém precisa colar código nem requisitos — e ela descobre o resto do contexto sozinha.

A solução

A skill roda em quatro fases, e cada uma entrega um artefato que alimenta a próxima:

  1. Investigação: lê o diff, as discussões do merge request e o arquivo do Figma, e mapeia o que não acontece no clique — crons, filas, e-mails, lembretes, expirações.
  2. Requisitos: monta uma matriz em que cada requisito carrega sua fonte e suas variáveis de estado (status, papel, feature flag, fuso horário, vazio ou cheio, primeira vez ou recorrente).
  3. Plano de testes: uma tabela em que todo requisito ganha pelo menos um caso, além de casos de controle, verificação de estado final, consistência após transições e combinações de estado em pairwise.
  4. Execução (opcional): roda os casos por prioridade com Playwright, marcados PASSED, FAILED ou NOT TESTED, e publica um relatório focado em bugs, com traces.

Regras que nasceram de execuções reais: asserções visuais comparam screenshots com o Figma, dinheiro ou dado clínico é lido de volta do banco, e evidência nunca é forjada — se um caminho é inalcançável pelo produto, o relatório diz isso.
