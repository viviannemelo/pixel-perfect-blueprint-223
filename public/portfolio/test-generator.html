Test Generator

One command, /test-generator ENG-1234, takes a Jira ticket from requirements to evidence-backed testing — and, on request, an automated regression pack that keeps protecting the product after release.

Um comando, /test-generator ENG-1234, leva um ticket do Jira dos requisitos aos testes com evidências — e, quando solicitado, a um pacote de regressão automatizado que continua protegendo o produto após a entrega.

The problem

Testing depth used to depend on who picked up the ticket and how much time they had. Under pressure, linked attachments went unopened, screens weren't compared field by field with Figma, and the impact on other features went unchecked. Bugs lacked owners, sprints or screenshots, while results were scattered across Jira comments.

Once the ticket shipped, the testing was gone. The next regression started from zero.

The solution

A repeatable QA playbook that follows the same steps for every ticket:

  1. Check the setup: confirms VPN, Jira, Figma, Playwright, Datadog, local repositories and Node. If something is missing, it stops and explains what.
  2. Understand: reads the ticket, linked issues, comments, attachments and Figma. It documents acceptance criteria, business rules, every screen field and what must not happen. Unclear rules are checked with the reporter or developer instead of guessed.
  3. Design cases: compares code changes with requirements, flags missing implementations or undocumented behavior, and creates a plain-language plan covering happy paths, validation, negative and edge cases, design conformance, regression, state combinations and time-based behavior.
  4. Execute: runs the plan in a real staging browser alongside Figma. Login stays manual. Every failure is reproduced with screenshots; bugs are filed only after approval, with the sprint, developer and task link. Each round ends with one Jira comment and a go / no-go recommendation.
  5. Automate, on request: turns cases protecting money, state changes and fragile rules into an E2E pack. Data is prepared through the API, actions run through the UI, and results are verified in both. A README and merge request accompany the pack, which re-runs on scheduled builds.

Results

  • Consistent testing depth, regardless of who runs the ticket.
  • Actionable bugs with reproduction steps, evidence, severity and an owner.
  • One place for results: a single Jira comment per round.
  • Testing that outlives the release: the E2E pack catches regressions when the code changes again.

Key lesson: testing a ticket is only the beginning. Turning the important cases into repeatable regression coverage makes the quality work last.

O problema

A profundidade dos testes dependia de quem pegava o ticket e do tempo disponível. Sob pressão, anexos de tarefas relacionadas não eram abertos, telas não eram comparadas campo a campo com o Figma e o impacto em outras funcionalidades passava despercebido. Bugs ficavam sem responsável, sprint ou screenshots, enquanto os resultados se espalhavam por vários comentários no Jira.

Depois da entrega, os testes se perdiam. A próxima regressão começava do zero.

A solução

Um roteiro de QA repetível que segue os mesmos passos em cada ticket:

  1. Verificar o ambiente: confirma VPN, Jira, Figma, Playwright, Datadog, repositórios locais e Node. Se algo estiver faltando, interrompe o processo e explica o que falta.
  2. Entender: lê o ticket, tarefas relacionadas, comentários, anexos e Figma. Documenta critérios de aceite, regras de negócio, cada campo das telas e o que não deve acontecer. Regras ambíguas são esclarecidas com o autor ou desenvolvedor, sem adivinhações.
  3. Planejar os casos: compara as alterações no código com os requisitos, aponta implementações ausentes ou comportamentos não documentados e cria um plano em linguagem clara, cobrindo fluxo principal, validações, cenários negativos, limites, conformidade visual, regressão, combinações de estado e comportamentos dependentes de tempo.
  4. Executar: roda o plano em um navegador real no staging, com o Figma ao lado. O login permanece manual. Cada falha é reproduzida com screenshots; bugs só são registrados após aprovação, com sprint, desenvolvedor e link da tarefa. Cada rodada termina com um comentário único no Jira e uma recomendação de liberar ou não liberar.
  5. Automatizar, quando solicitado: transforma os casos que protegem valores financeiros, mudanças de estado e regras frágeis em um pacote E2E. Os dados são preparados pela API, as ações passam pela interface e os resultados são verificados nas duas. O pacote inclui README e merge request e roda novamente nas execuções agendadas.

Resultados

  • A mesma profundidade de testes, independentemente de quem executa o ticket.
  • Bugs acionáveis, com passos de reprodução, evidências, severidade e responsável.
  • Resultados centralizados: um único comentário no Jira por rodada.
  • Testes que sobrevivem à entrega: o pacote E2E detecta regressões quando o código muda novamente.

Principal aprendizado: testar um ticket é só o começo. Transformar os casos importantes em uma cobertura de regressão repetível faz o trabalho de qualidade durar.
