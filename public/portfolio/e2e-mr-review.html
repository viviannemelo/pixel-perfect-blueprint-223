E2E MR Review

An AI skill that reviews only the E2E tests in a merge request, like a senior automation QA would: six rules, verified findings and inline comments with ready fixes.

Uma skill de IA que revisa só os testes E2E de um merge request, como faria um QA sênior de automação: seis regras, achados verificados e comentários na linha exata com a correção pronta.

The problem

A badly written E2E test can pass while the feature is broken, or fail randomly in CI. The most common causes are a fixed waitForTimeout, a selector tied to the HTML structure or a check done only through the API. These problems slip easily through a regular code review, because the code "works". Later they become flaky tests that nobody trusts.

How it works

You call /e2e-mr-review with the MR number and the skill reviews only the E2E tests, as a senior automation QA would:

  • Reads the diff. Fetches the MR's changes.
  • Filters the scope. Ignores product code, unit tests and lockfiles, keeping only E2E specs, helpers, fixtures and configs. It also reads the project's READMEs and conventions so it doesn't flag as a problem something the team does on purpose.
  • Reviews against six rules: locators; waits and synchronization; design patterns; anti-flaky practices; test data; validation through the UI.
  • Verifies each finding. Checks that the line really belongs to the MR, that the quoted code is correct and that the suggested fix works in the project. It discards what doesn't hold up and gives the rest a severity: Blocker or Improvement, with high, medium or low priority.
  • Comments on the MR. Posts each problem on the exact line, with the cause and a suggested fix, plus a summary note with the verdict (approve, approve with improvements or request changes). With --dry-run, it shows the review only in the chat. The skill never edits code, never approves and never merges.

The result

The problems that make a test flaky or misleading are caught before the merge, with an explanation and a ready fix. That way, the MR's author learns the pattern instead of just receiving a "fix this".

O problema

Um teste E2E mal escrito pode passar com a funcionalidade quebrada, ou falhar aleatoriamente no CI. As causas mais comuns são um waitForTimeout fixo, um seletor preso à estrutura do HTML ou uma verificação feita só pela API. Esses problemas passam fácil num code review comum, porque o código "funciona". Depois viram testes instáveis que ninguém confia.

Como funciona

Você chama /e2e-mr-review com o número do MR e a skill revisa só os testes E2E, como faria um QA sênior de automação:

  • Lê o diff. Busca as mudanças do MR.
  • Filtra o escopo. Ignora código de produto, testes unitários e lockfile e fica só com specs, helpers, fixtures e configs de E2E. Também lê os READMEs e as convenções do projeto para não apontar como problema algo que o time já faz de propósito.
  • Revisa contra seis regras: locators; waits e sincronização; padrões de design; práticas anti-flaky; dados de teste; validação pela tela.
  • Confere cada achado. Verifica se a linha é mesmo do MR, se o código citado está certo e se a correção sugerida funciona no projeto. Descarta o que não se sustenta e dá uma severidade ao resto: Blocker ou Improvement, com prioridade alta, média ou baixa.
  • Comenta no MR. Posta cada problema na linha exata, com a causa e uma sugestão de correção, mais uma nota de resumo com o veredito (aprovar, aprovar com melhorias ou pedir mudanças). Com --dry-run, mostra a revisão só no chat. A skill nunca edita código, nunca aprova e nunca faz merge.

O resultado

Os problemas que tornam um teste instável ou enganoso são pegos antes do merge, com uma explicação e uma correção pronta. Assim, o autor do MR aprende o padrão em vez de só receber um "arruma isso".
