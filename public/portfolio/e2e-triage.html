E2E Triage

An AI skill that runs right after the scheduled E2E pipeline and does the triage a person would do: filters, reruns, classifies, fixes test errors and reports a short summary.

Uma skill de IA que roda sozinha logo depois do pipeline agendado de E2E e faz a triagem que uma pessoa faria: filtra, roda de novo, classifica, corrige erros de teste e reporta um resumo curto.

The problem

Every day at 11:00 the scheduled E2E test pipeline runs. When it goes red, someone has to stop what they're doing and investigate each failure: read the log, run the test again and figure out whether the error is in the test or in the product. It's repetitive, slow work. When nobody does it, the pipeline stays red for days and the team stops trusting it.

How it works

The skill runs on its own right after the pipeline and does the triage a person would do:

  • Filters. Separates failures that are already known and tests that failed once but passed on retry. Those don't become alerts.
  • Reruns. Runs each failure again, changing nothing, on the same commit the pipeline used. If it passes, it was flakiness, and it flags it for someone to look at.
  • Classifies. Looks at what changed in the code since the last green run, the test trace, the execution time and, if needed, reproduces it on staging. Each failure becomes one of three: test error, product bug or undetermined.
  • Fixes. If the error is in the test (a button that changed its name, for example), it adjusts the test, confirms it passes and opens a draft MR. It never weakens an assertion to make a test pass and never touches product code.
  • Reports. Sends a single short message to the QA channel with what was fixed, the bugs with each spec's owner, what needs a person and what was already known. If everything is green, it sends nothing.

The result

Whoever arrives has a ready summary and an MR to review, instead of a red screen to investigate from scratch.

O problema

Todo dia às 11:00 roda o pipeline agendado de testes E2E. Quando ele fica vermelho, alguém precisa parar o que está fazendo e investigar cada falha: ler o log, rodar o teste de novo e descobrir se o erro é do teste ou do produto. É um trabalho repetitivo e demorado. Quando ninguém faz, o pipeline fica vermelho por dias e o time para de confiar nele.

Como funciona

A skill roda sozinha logo depois do pipeline e faz a triagem que uma pessoa faria:

  • Filtra. Separa as falhas que já são conhecidas e os testes que falharam uma vez mas passaram no retry. Esses não viram alerta.
  • Roda de novo. Executa cada falha outra vez, sem mudar nada, no mesmo commit que o pipeline usou. Se passar, era instabilidade, e ela marca para alguém olhar.
  • Classifica. Olha o que mudou no código desde o último verde, o trace do teste, o tempo de execução e, se preciso, reproduz no staging. Cada falha vira um destes três: erro do teste, bug do produto ou indeterminado.
  • Corrige. Se o erro é do teste (um botão que mudou de nome, por exemplo), ela ajusta o teste, confirma que passa e abre um MR em draft. Ela nunca enfraquece uma asserção para o teste passar e nunca mexe em código do produto.
  • Reporta. Manda uma única mensagem curta no canal de QA com o que foi corrigido, os bugs com o dono de cada spec, o que precisa de uma pessoa e o que já era conhecido. Se tudo estiver verde, não manda nada.

O resultado

Quem chega tem um resumo pronto e um MR para revisar, em vez de uma tela vermelha para investigar do zero.
